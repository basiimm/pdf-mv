Verdict

The workspace shell is in good shape. Everything around it isn't consistent yet. Home, the tabs, native panels and the green Spectrum-style chrome are right. The problems are underneath:

  • 119 BentoPDF tool pages are restyled at runtime by CSS that only takes effect after JavaScript runs. That delay is the flicker.
  • Nine tools never receive the override at all.
  • The shared alert, loader and page-thumbnail components in ui.ts are still BentoPDF's.
  • There is no real token scale yet: 14 control heights, 22 font sizes and 15 corner radii.

Fixing the boot order removes the flicker in days. Consistency after that comes from one token file, one component kit and a lint gate that stops BentoPDF classes from coming back.

1. Why BentoPDF flashes when you switch tools

I measured this in the dev app by opening Edit PDF text from Home and sampling the tool iframe every 10 ms:

Empty frame
BentoPDF gray-900 · rgb(17,24,39)
Studio theme
0 ms67 ms188 ms256 ms

That's with a warm cache. On a cold load the legacy segment stretches to about a second, which matches what you described: the studio theme waits on a module graph of roughly 1.5 MB (pdfjs, the full lucide icon set and main.ts).

What happens, in order

  1. workspace-tools.ts:544–579 creates the iframe and shows it straight away (:462 hidden=false). Nothing waits for load or styling.
  2. The tool page's <head> loads Tailwind styles.css, which blocks rendering. The body is class="antialiased bg-gray-900" with the navbar partial, bg-gray-800 cards and "Back to Tools".
  3. First paint is BentoPDF. Every studio override is gated by html[data-studio-theme] (41 rules), body[data-studio-tool] (56) or .workspace-embedded-tool (18). JavaScript adds all three.
  4. The deferred modules run. studio-theme.ts:93 sets the theme attribute, :235 marks the tool, and workspace-tool-bridge.ts:5 adds the embedded class. In dev, studio-theme.css doesn't exist until this moment. Everything then restyles at once.
  5. Loading files adds .studio-has-files, so the layout jumps a second time.

Where it repeats:

  • The frame key includes the document revision (:541), so every edit rebuilds the iframe.
  • "Use current PDF" reloads the frame with frame.src = frame.src (:478).
  • Switching conversions deletes the frames (:125–133).

Workspace itself: dark-mode users get one light frame first. color-scheme is set from JavaScript, and workspace.css:1–10 has its own blue-grey --studio-* values that paint before the studio theme applies.

Why the old UI is still in the codebase

PDF.mv is a fork of BentoPDF. The repo carries 1,031 commits of upstream history, and in BentoPDF a tool's screen and its processing code are the same thing. Each of the 119 src/js/logic/*-page.ts files finds its buttons and fields by ID and then runs the PDF engine. There are 2,008 getElementById calls. For example, compress-pdf-page.ts:182–189 reads #file-input, #drop-zone, #compress-options and #process-btn. It also writes Tailwind HTML strings and uses BentoPDF's shared alert and loader. Delete the HTML and the engine stops working.

Our redesign therefore followed the original plan: reuse the upstream engines and avoid a full frontend rewrite. The workspace loads each original page in an iframe and restyles it after load. That kept all 118 tools working from day one and made upstream BentoPDF changes easy to pull in. The cost is what you're seeing:

  • Every tool paints twice: BentoPDF's look first, then ours.
  • The old markup, Tailwind classes, navbar partials and landing pages all still ship.
  • The styling layer can only hide the old UI, not remove it.

The boot-order fixes below remove the flicker, but they're a stopgap. The real fix is to separate each engine from its page:

  • Extract the processing into headless functions: engines/compress.ts takes (bytes, options, onProgress) and returns a Blob.
  • Drive those functions from our own panels inside the PDF view (§5b).
  • Delete the page HTML, the Tailwind remap layer and the partials.

Native Rotate, Delete, Merge and Watermark already work this way. The trade-off is that upstream UI changes stop merging cleanly, while engine fixes stay easy to bring over.

Target flow: every tool, the same six states

  1. Pick: from Home, search/⌘K, or the document tool list. The task tab opens instantly with a panel skeleton.
  2. Source: the open document is used automatically. Otherwise a SourcePicker appears inside the panel, with a large drop target on the empty canvas that opens the same picker.
  3. Configure: essential fields with defaults, Advanced collapsed, preview in the central canvas when the output is visual.
  4. Run: the footer button becomes a progress bar with phase and cancel. Settings stay put.
  5. Result: a ResultCard in the panel. The PDF opens in a new tab and the original stays untouched.
  6. Recover: an InlineAlert says what happened, confirms the document is safe, and offers one recovery action, with details collapsed.

5b. One PDF view for every tool

Goal: choosing a tool never swaps the user into a different screen. The document, thumbnails, zoom and page position stay where they are. The tool shows up in only three places, always the same three:

  • Toolbar row above the page: modes and in-canvas tools.
  • On the page itself: handles, placed fields and previews.
  • Right panel: options, the primary action and the result.

The viewer already has a toolbar-mode API: host.editMode(id, 'annotation-toolbar' | 'shapes-toolbar' | 'redaction-toolbar') in workspace-tools.ts:183–212. Every tool should use that same mechanism.

8. Usage rules

One accent action per surface

Do use the accent pill for the single main action in a panel footer or dialog.

Don't use accent for decoration, links next to buttons, or several actions in a row.

Tokens only

Do reference --ds-* tokens in every component.

Don't add hex, rgb() or Tailwind gray-/indigo-/blue- classes anywhere in src/. Stylelint and a CI grep fail the build.

Size by context

Do use M (32) in desktop chrome, L (40) for panel footer actions, 44 minimum on coarse pointers.

Don't invent heights, or use text below 12px.

Selection vs focus

Do show selection with --ds-selected fill; focus is always a 2px accent ring offset by 2px.

Don't use an outline to mean "selected".

One PDF view

Do put tools in the toolbar row, on the page, or in the right panel, and keep zoom and page position.

Don't hide the viewer, open a second preview, or ask to upload a document that's already open.

Panels, not pages

Do put every tool inside the ToolPanel scaffold, with results and errors inline.

Don't open blocking modals for success, or show breadcrumbs or "Back to Tools" in the workspace.

Defaults first

Do ship defaults so Apply works immediately; hide rarely changed settings under Advanced.

Don't keep the primary action disabled until the user makes choices.

Honest progress

Do show progress after 400 ms, with phase and units, and Cancel when cancelling really stops the work.

Don't show a Cancel that does nothing, or a spinner with no label.

Errors that recover

Do write: what happened · your document is safe · one action · details collapsed.

Don't show error.message, apologize, or leave a dead end.

Motion with purpose

Do animate drawers, sheets and toasts with transform and opacity, using the motion tokens. Keep tab switches and keyboard actions instant.

Don't stagger or animate on page load. Reduced motion = opacity only.

Copy

Do use sentence case, verb-first buttons ("Merge PDFs", "Download ZIP"), and "PDF.mv" as the only product name.

Don't write "PDF Studio", "Process", "Submit", or star-studded marketing copy inside the app.

The phases are in order: each depends on the one before. Model assignments aim for the lowest cost that can do the work reliably.

Opus 5 (main) · ~2–3 days

Foundations and guardrails
